# 0026. Media transfer by path or chunks, upload retry, and media retry

- Status: Accepted
- Date: 2026-11-01
- Evidence: issue #28, its plan review, ARCHITECTURE §14 "Measured for Media (#28)", and the tests named below

## Context

Issue #28 moves files between .NET and WhatsApp through the sidecar at constant memory (§13 invariant 8), verifies a download before any plaintext reaches .NET, retries uploads, and recovers expired media through the phone.
Reading whatsmeow at the pin for it showed facts the design had to follow [observed: ARCHITECTURE §14 "Measured for Media (#28)"]:

- `UploadReader` makes a new media key on every call and encrypts into the temporary file it is given; passing the user's file as that file overwrites it with ciphertext (upload.go:114-154).
- whatsmeow makes one POST to the first host and never retries; its upload errors are untyped strings (upload.go:243-302).
- A failed download check leaves ciphertext, or unchecked plaintext, in the file whatsmeow wrote (download-to-file.go:121-161, 209-246).
- The phone's media retry answer is encrypted with the media key, and names only the message (mediaretry.go:123-176); whatsmeow acknowledges its notification whatever the handler returns (notification.go:510-511).
- Go 1.27's `os.Root` refuses `..` and symlinks that leave the root, absolute symlinks included, on Unix and Windows (`go doc os.Root`).

## Decision

- **Path or chunks.** A path inside `--media-root` is handed over: the sidecar opens it through one `os.Root` and refuses one that leaves the root. Anything else travels in chunks of at most 65,536 bytes, the header first. The .NET client decides by the path as written, compared as Go's `filepath.Rel` compares it: by case, except on Windows (.NET's own `Path.GetRelativePath` ignores case on macOS too, and Go would then refuse the path). The sidecar's `os.Root` is the confinement. With no root, every transfer uses chunks.
- **Opened, then checked.** Each upload attempt opens the path again through the root, non-blocking, and checks the handle it opened: anything but a regular file is `INVALID_ARGUMENT` and not retried. A check before the open would race a swap, and opening a FIFO with no writer blocks past the call's context [observed: `TestAPathSwappedForAFIFOIsRefusedAtOnce` without `O_NONBLOCK`]. On Windows a path under a directory is never a FIFO [inferred].
- **Missing files.** A missing file, or a missing directory, under the root throws what it throws outside it, `FileNotFoundException` or `DirectoryNotFoundException`: the client checks before it hands the path over. A file removed between that check and the sidecar's open is `WhatsmeowValidationException`.
- **Temporary files.** The sidecar's own are in `<database>.tmp/`, 0700, emptied at every start (one sidecar owns the database, so the directory next to it), never in `/tmp`, which may be a tmpfs. A download to a path is written to `.<name>.<random>.part` next to it, through the root, 0600, and renamed over the destination once verified; any failure removes it. Outside the root the .NET client does the same itself. A crash can leave a `.part` file, never a partial destination.
- **Verification first.** A chunked download is downloaded and verified into the sidecar's temporary directory before the first chunk is sent. `ErrInvalidMediaSHA256` after a valid MAC is delivered with a warning, as mautrix does; every other failed check is `INTERNAL` and delivers nothing.
- **Upload retry.** 3 attempts, 1 s and 2 s apart, within the call: each is a whole `UploadReader` from a source that can be read again (the file under the root, or the spooled chunks), so each has its own media key. Not retried: the call ending, the session going offline, and our own file failing to read or write. Every attempt failing is `INTERNAL`. whatsmeow's errors carry no status, so a permanent rejection costs the two extra attempts [inferred: WhatsApp answers some uploads with a permanent 4xx]. A retry does not force a new media connection: whatsmeow never forces one itself, its cache lives for the TTL WhatsApp gave (mediaconn.go:44-58), forcing it needs `DangerousInternals().RefreshMediaConn` (internals.go:306-308), and an untyped error cannot tell a stale auth from any other failure.
- **No credential in an error.** whatsmeow's request errors are `*url.Error`s that print the whole URL, whose query is the media connection's auth on an upload and the CDN's signature on a download (upload.go:251-288, download-to-file.go:104). The slice cuts the query from that URL before it logs or returns the error, and whatsmeow's own log lines go through a logger that cuts the query from every URL in them (`internal/log`).
- **`MEDIA_EXPIRED`.** 403, 404 and 410 from a download (`ErrMediaDownloadFailedWith4xx`) are the new reason `MEDIA_EXPIRED`, `MediaExpiredException` in .NET.
- **Media retry.** `RequestMediaRetry` stores the request, the message and its `MediaRef`, in `media_retry` (schema step 3, a session's rows go with it), then sends the receipt, so an answer that comes at once or after a restart finds it. The Events slice's handler maps the answer through the media slice's `events.Mapper` (`func(sessionID string, evt any)`): it reads the session's request for the answer's message id, preferring the one in the answer's chat (the answer may name the chat by LID where the request used the phone number, or the other way [unknown: #10]), decrypts the answer with its media key, SQLite and a few bytes of AES-GCM, and records a `MediaRetryEvent` with the media at its new path, or the failure.
- **A final answer settles its request.** The media at its new path, `NOT_FOUND`, not on the phone, and `DECRYPTION_ERROR` (the phone could not read the request, which asking again with the same key would repeat) delete the request's row, with its media key; a general error, an unknown code, or an answer that does not decrypt keep it for a later answer [inferred: WAMmsRetry.proto names no retry semantics]. A request the phone never answers stays until its session is deleted. This amends §13 invariant 1: besides the outbox, the handler deletes the media retry request a final answer settled, a local SQLite write that never blocks on .NET, the network or media. The delete comes before the outbox write; if that write fails, the answer is lost as it would be anyway, because whatsmeow acks the notification whatever the handler returns (notification.go:510-511).
* **Malformed encrypted answers.** An encrypted answer with an IV other than 12 bytes or no ciphertext becomes the same unspecified failure as an answer that does not decrypt, retaining the request for a later answer.
  The check precedes whatsmeow's decryption, whose AES-GCM call panics on an invalid IV [observed: #133, `internal/media/retry_malformed_test.go`, pin `56e5ad0581ce` mediaretry.go:123-135, util/gcmutil/gcm.go:25-32].
  Plain error answers have no encrypted bytes and keep their existing meanings, including code 2 as not on the phone [observed: mediaretry.go:125-129; `internal/media/retry_test.go`].
- **Online.** Every media RPC needs the session Connected or CaughtUp, through `session.(*Service).Online`; the slice type-asserts the client to its own interface, `INTERNAL` when it is not one.
- **`MediaRef`.** Upload's fields and the media type: no mimetype, which the upload does not produce (it is message metadata, #29). In .NET a sealed record with `ImmutableArray<byte>` keys and hashes and a content `Equals`: a reference stored and read back equals the one it came from. docs/guidelines/tests.md names this as the allowed case of element-wise equality.
- **The .NET API** is flat on `IWhatsAppClient` (ADR 0025): `UploadMediaFileAsync`, `UploadMediaAsync(Stream)`, `DownloadMediaFileAsync`, `DownloadMediaAsync(Stream)`, `RequestMediaRetryAsync`, and the `MediaRetryReceived` event. The path members have their own names: PublicAPI's RS0026 refuses overloads that each take an optional token.
- **The fake WhatsApp** encrypts and verifies with whatsmeow's own `cbcutil` and `hkdfutil`, and keeps each upload's ciphertext in a file next to the database, so its hashes, MAC and keys are what whatsmeow makes, a failed check leaves what whatsmeow leaves, and a `MediaRef` downloads after a sidecar restart.

## Consequences

- An upload in chunks writes the plaintext once more to disk (the spool) so a retry can read it again.
- No upload dedup cache: re-sending a stored `MediaRef` is how an application skips an upload.
- A stream download can leave the start of the verified file in the caller's stream when the transfer breaks; the path download is all or nothing.
- Memory of a 300 MiB transfer on osx-arm64 CI, managed heap growth upload / download: +11 to +13 / +21 to +23 MiB when the transfer test runs alone, +27 to +29 / +41 to +44 MiB inside the whole suite, with HTTP/2 dynamic window sizing on or off alike [observed: CI run 41401548064, `DOTNET_SYSTEM_NET_HTTP_SOCKETSHTTPHANDLER_HTTP2FLOWCONTROL_DISABLEDYNAMICWINDOWSIZING` 0 and 1, alone twice each and in the suite once]. So the HTTP/2 receive window is ruled out, and the extra growth comes with the rest of the suite on that runner; what holds it is [unknown]. Linux and Windows CI and a local Apple Silicon Mac stay at +9 to +21 MiB in the suite. It does not grow with the file: buffering the upload measured +512 MiB.
- An upload the sidecar refuses after the header ends the call while the client may still write chunks; the client then reads the call's status, so the error is the sidecar's reason, never the cut-short write (`Upload_RefusedWhileChunksStillGoOut_ThrowsTheSidecarsReason`).
- Tests: `internal/media` (paths, chunks, retries, MAC, expiry, cancellation, the media retry mapping and its settled requests, a URL query in an error, a path swapped between attempts, a 256 MiB heap check), `internal/log` (the URL cut), `internal/fakewhatsapp/media_test.go`, `internal/store` step 3, and `Whatsmeow.IntegrationTests/Media/` (the FullCycles, the restart, and a 300 MiB transfer per transport at constant memory, on sidecars of its own).
