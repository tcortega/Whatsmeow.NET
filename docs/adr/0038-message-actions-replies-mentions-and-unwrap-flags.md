# 0038. Message actions: reactions, edits and revokes as sends, replies and mentions as send options, and what the unwrapping said

- Status: Accepted
- Date: 2026-11-02
- Evidence: issue #30, its plan review, the review of PR #87, ARCHITECTURE §14 "Measured for Message actions (#30)", and the tests named below
- Uses: [ADR 0025](0025-messaging-and-receipts.md) (the send queue and records), [ADR 0033](0033-media-messages.md) (the media sends and the content mapping), [ADR 0036](0036-testing-package-and-fake-client.md) (the fake client)

## Context

Issue #30 sends reactions, edits, revokes, quoted replies and mentions, delivers the ones other people send, and stops dropping what whatsmeow's unwrapping of a received message said: ephemeral, the chat a message from the account's own phone went to, and the message as it was received.
A group `READ_SELF` receipt also lacked the sender of the messages it covers.
Reading whatsmeow at the pin and mautrix-whatsapp `5dd621f` for it showed facts the design had to follow [observed: ARCHITECTURE §14 "Measured for Message actions (#30)"]:

- whatsmeow builds a reaction, a revoke and an edit itself (send.go:536-635), and names the target with `BuildMessageKey`, which needs the account's own JID and LID: an empty sender or the account's own is the account's message; another's is someone else's, with the participant outside a direct chat.
- A received reaction, edit or revoke is an ordinary gated `events.Message` (message.go:1172-1178); an edit comes unwrapped from its `EditedMessage` as a `ProtocolMessage` of type `MESSAGE_EDIT`, a revoke as one of type `REVOKE`, which is the type's zero value.
- `UnwrapRaw` removes the device-sent, ephemeral, view-once, edit and other wrappers and keeps the raw message beside the unwrapped one, the same pointer when it removed none (types/events/events.go:377-425).
- mautrix replies with `StanzaID`, `Participant`, a `QuotedMessage` that is the quoted text as a conversation (empty when it has none) and `QuotedType EXPLICIT`, mentions in `MentionedJID`, and reads a message as disappearing from its `ContextInfo.Expiration` (pkg/msgconv/from-matrix.go:56-126, 344-375; from-whatsapp.go:257-260).
- mautrix reads a received key's sender (`KeyToMessageID`, pkg/msgconv/wa-poll.go:97-132): the actor, without a device, when the key is `FromMe`; else its participant, `c.us` read as `s.whatsapp.net`; else, in a direct chat, the chat when the actor is the account and otherwise the account; and no message for a group key with neither.
- whatsmeow marks a message `IsFromMe` when its sender's user is the account's JID's or LID's (message.go:110-111, 141-149), and `BuildMessageKey` compares only the user too (send.go:511-523).
- Two typed-send overloads with optional parameters, one with a `SendOptions` after the content, made `SendTextAsync(chat, text, null)` and `SendTextAsync(chat, text, default)` ambiguous, CS0121, for text and every media kind, on `IWhatsAppClient` and `FakeWhatsAppClient` [observed: the PR #87 review's compile probe].
- A receipt's `MessageSender` is its `recipient` attribute (receipt.go:77).

## Decision

- **Three RPCs, sends like the others.** `SendReaction`, `SendEdit` and `SendRevoke` go through the same `send`: one per-session queue, the same pacing, flight, `sent_message` record and classification (ADR 0025). The `client_message_id` is the action's own id, so a repeat returns its first result whatever kind either send was, and an unknown outcome is never sent again (invariant 10).
  The message is whatsmeow's own: the slice's small interface gains `BuildReaction`, `BuildRevoke` and `BuildEdit`, called once the session is online, so a whatsmeow change to them stays inside whatsmeow.
  The fake WhatsApp copies the three; a test compares its builds with whatsmeow's own on the same device, timestamps aside.
- **The target.** A target is `MessageKey { Id, Sender? }`: a null sender, or the account's own JID, is the account's own message, as `BuildMessageKey` reads it; another member's in a group is an admin revoke. WhatsApp's refusal of a revoke is `WHATSAPP_ERROR`, `WhatsAppErrorException` with its `Code`, recorded and repeated.
  An edit is text only, of the account's own message; nothing checks an edit window, because the sidecar keeps no messages (§1), and whatsmeow's `EditWindow` is read nowhere.
- **Replies and mentions are send options.** `SendTextRequest` and `SendMediaRequest` gain `reply_to` (`MessageReply { id, sender, quoted_text }`) and `mentions`; the sidecar builds the context as mautrix does, on an extended text for a text (a plain conversation without either) and on the media message for media, inside a captioned document's wrapper.
  A reply without a sender quotes the account's own message: the sidecar names the account without a device as whatsmeow names it when it sends to the chat (`SendMessage`'s `ownID`, send.go:304-365): by its LID in a direct chat, by phone number or LID, since whatsmeow sends a phone number's message to its LID, and in a LID-addressed group; by its phone number in any other group, and while the LID is unknown (`session.(*Service).Device`). A group's addressing mode is only in whatsmeow's private group cache (group.go:657-711, 1023), which no exported call reads, and whatsmeow's store keeps none [observed], so an own reply in a group asks WhatsApp for the group's info (`GetGroupInfo`, which fills that cache for the send). That costs one group-info request per own reply in a group, and only there: it is made in the send's paced turn, when the queue builds the message, so it waits for the sends before it, and a repeat answered from its record never makes it. A failed build does not spend the turn. WhatsApp refusing the request fails the send as whatsmeow's own read would, and sends nothing. It reads the device only when the send is built, after the send's record, so a repeat of a recorded reply gets its record even once the session logged out. Whether WhatsApp resolves the quote either way, and whether it needs a participant at all, are [unknown] (#36).
  In .NET each typed send is one method, the options optional after the id: `SendTextAsync(Jid chat, string text, MessageId? id = null, SendOptions? options = null, CancellationToken cancellationToken = default)`, and the same for the five media kinds. This is a pre-1.0 signature change: the token moves one place, behind the options, so a positional `(chat, text, id, ct)` call stops compiling (CS1503) and names `cancellationToken:` instead. Nothing has shipped, and the alternative, an overload per send with the options after the content, made a `null` or `default` third argument ambiguous (Context). With one method, `null`, `default` and a message id there are the id, and the options go by name or after the id; `MessageActionCallTests` pins that.
- **Received actions are content.** `ReactionContent { Target, Emoji }` (empty is a removal), `EditContent { Target, Content }` and `RevokeContent { Target }`, whose remover is the event's source.
  The sidecar reads the key, because only it knows the account: `MessageEvent` gains `target` (7), a `MessageTarget { id, sender }`. Its sender reads as mautrix reads it (Context), without a device, and is empty for the account's own message however the key names the account, by phone number or LID and from any device, so a null `Target.Sender` always means the account's message. A key that names no message, one without an id, with a participant that is not a user's JID (one without a server would read as the empty JID, the account's; a group's is no sender), or in a group neither the actor's nor naming a participant, has no target, and the action is unknown content, as other malformed content is; so is, in .NET, a target whose sender does not parse.
  A protocol message is a revoke or an edit only when its type is set.
- **What the unwrapping said.** `MessageEvent` gains `ephemeral` (4), `device_sent_destination` (5) and `raw_message` (6), the last only when whatsmeow removed a wrapper, so a plain message is not recorded twice. No edit flag: `EditContent` is the edit. No document-with-caption, Lottie, bot-invoke or V2 view-once flag: the content mapping already handles what they wrapped, and `Raw` shows the wrappers.
  A reply's quote is named the same way: `MessageEvent` gains `reply_to` (8), a `MessageTarget` read from the context of the content kinds the client maps, its sender the context's participant, a user's without a device and empty for the account's own message, so a null `QuotedMessage.Sender` always means the account's too. A quote whose participant is missing or is not a user's JID could only read as the account's, so the message is no reply. The message itself is not changed, so `Raw` stays the message as received.
  `MessageReceived` gains `ReplyTo` (`QuotedMessage { Id, Sender?, Content? }`), `Mentions`, `IsEphemeral` (the wrapper, or an expiration above 0, as mautrix reads it), `DestinationChat`, and the `[Experimental("WMN1001")]` `Raw`, the message as received, or the message itself when nothing was unwrapped. None is required, so a record built before them still compiles.
  `ReceiptEvent` gains `message_sender` (5), `ReceiptReceived.MessageSender`; the receipt's natural key is unchanged.
- **`Raw` is outside the record's equality.** `MessageReceived` compares every stable member, the mentions by content, and leaves out `Raw`: its type is whatsmeow's, which changes with every bump, and the equality of a stable record must not depend on it. Every message comes with a `Raw`, so including it would make every record a test builds unequal to the one delivered; a test of `Raw` compares it on its own.
  The experimental attribute does raise WMN1001 inside its own assembly, so the mapping that fills it carries a justified pragma [observed: the build].
- **The fake WhatsApp** gains the three builders, `RefuseNextSend` (WhatsApp answers the next message node with an error code, send.go:468-470; a send `HoldNextSend` holds too is refused at once and leaves nothing held), and `DeliverReceiptRequest.message_sender`; received actions, replies, mentions and wrappers need no control, since `DeliverMessage` already unwraps a raw message with whatsmeow's own `UnwrapRaw`.
- **The consumer fake** implements the three members and the options of the six typed sends, which it records after the id, null when none were given.

## Consequences

- A key's chat is the chat given, while whatsmeow sends a phone number's message to its LID; whether WhatsApp matches a reaction, revoke or quote whose key names the phone number is [unknown], and so are the address form a LID-addressed group needs for a mention, what WhatsApp answers a non-admin revoke, and whether it refuses or drops a late edit. The Phase 2 exit live run (#36) records them.
- The History slice maps its messages with the same `events.MessageEvent` ([ADR 0035](0035-history-sync-that-never-delays-live-traffic.md)), with the session's device, so a history message's event carries the new fields and its target too; `HistoryMessage` does not show the flags yet, and its content maps reactions, edits and revokes as a live message's does.
- `MessageReceived` prints every member but `Raw`: protobuf's text of a message carries its media keys. The printing is hand-written, so a test fails when a public member is left out of it.
- The messaging slice's INVALID_ARGUMENT texts name the field and the rule, never the JID they refused, so ADR 0039's FullCycle `SendText_ToADevice_ThrowsWithoutTheNumber` checks the rule's text; the redaction of an echoed JID stays checked on the server's own (`TestAStatusCarriesNoNumberOrCredential`).
- Calls written before this change that pass the token fourth, `SendTextAsync(chat, text, id, ct)`, must name it.
- `device_sent_destination` goes through `server.Text`, as every string from WhatsApp data does: it is a proto2 string, so whatsmeow passes invalid UTF-8 through.
- Polls stay #31, and a caption edit, a forwarded flag and a disappearing timer on send stay for `SendRawAsync`.
- Tests: `internal/messaging/action_test.go` (whatsmeow's own builds, validation, the context of a reply and mentions on every kind of send, the account's own reply by chat, a group's info read in the send's turn, never by a repeat, and refused, and its record after logout, one queue and record with the other sends), `internal/events` (the flags, the raw message, the target of every key form, the quote of every participant form), `internal/history` (a history reaction's target), `internal/messaging/receipt_test.go` (the messages' sender), `internal/fakewhatsapp/action_test.go` (the builders against whatsmeow's, `RefuseNextSend` alone and with `HoldNextSend`, the receipt's sender), `Whatsmeow.IntegrationTests/Messaging/MessageActionTests.cs` and `Whatsmeow.Testing.Tests/MessageActionCallTests.cs` (the typed sends' binding).
