# 0022. The outbox, the event stream and the dispatcher

- Status: Accepted
- Date: 2026-11-01
- Evidence: issue #8, its plan review, ARCHITECTURE §14 "Measured for Events (#8)", and the tests named below
- Supersedes: `busy_timeout(5000)` in [ADR 0003](0003-at-least-once-delivery-synchronousack-sqlite-outbox.md) and ARCHITECTURE §5; the `PortalEventBuffer` default in [ADR 0013](0013-whatsmeow-config-follows-mautrix-no-fork.md); the "gated" recovery of an undecryptable message in [ADR 0003](0003-at-least-once-delivery-synchronousack-sqlite-outbox.md) and ARCHITECTURE §1; the word "acked" in invariant 2

## Context

Issue #8 builds the no-loss path ([ARCHITECTURE §1](../ARCHITECTURE.md#1-goals-and-non-goals), §13 invariants 1-3): the outbox write in the whatsmeow event handler, `StreamEvents` and `AckEvents`, and the .NET reader, dispatcher and watermark ack.
Reading whatsmeow and mautrix at their pins for it showed facts the design had to follow [observed: ARCHITECTURE §14 "Measured for Events (#8)"]:

- For a decrypted message, whatsmeow's answer to WhatsApp after the handlers succeeded is a delivery receipt (`sendMessageReceipt`, message.go:489-497), not an ack; a failed handler sends nothing (message.go:459-462). Receipts and `w:gp2` notifications are answered with an ack (`maybeDeferredAck`, receipt.go:115-128).
- whatsmeow dispatches a message again from its decrypted-event buffer after a crash between our commit and its buffer clear (message.go:459-477, 545-552), so one event can be recorded twice.
- SQLite spends a seq on an `INSERT ... ON CONFLICT DO NOTHING` that inserts nothing [observed: `TestARedispatchedMessageKeepsItsSeqAndIsStreamedOnce`].
- The account's phone answers a re-request for an undecryptable message with a copy that whatsmeow dispatches from inside the phone's protocol message, and a handler that fails on that copy does not withhold the receipt (message.go:863-881, 1172-1175). Only the sender's resend is a gated message.
- With `SynchronousAck`, whatsmeow asks the phone at once on the first retry receipt (retry.go:493-497); `RequestFromPhoneDelay` applies only without it.
- mautrix-whatsapp sets `EnableDecryptedEventBuffer = PortalEventBuffer == 0` (pkg/connector/client.go:83), and mautrix-go's default `portal_event_buffer` is 64 (bridgev2/matrix/mxmain/example-config.yaml:57): by default the buffer is off, and the bridge queues an event and returns before it handles it (bridgev2/portal.go:364-385). It turns the buffer on exactly when handling is synchronous, which is our mode.

## Decision

- **Outbox schema.** `outbox(seq INTEGER PRIMARY KEY AUTOINCREMENT, session_id REFERENCES session ON DELETE CASCADE, dedupe_key, payload, UNIQUE(session_id, dedupe_key))`, `outbox_cursor(session_id REFERENCES session ON DELETE CASCADE, consumer, acked)`, and `session.last_seq`, the highest recorded seq, kept after its rows are deleted.
  AUTOINCREMENT, so a seq is never reused after the newest row is deleted (`TestASeqIsNeverReusedAfterTheNewestRowIsDeleted`).
- **Schema steps.** A database that outlives a build exists already: the owner's live-paired session (#7, #10). `CREATE TABLE IF NOT EXISTS` never changes an existing table, so the sidecar's tables are numbered steps in `internal/store`, tracked in SQLite's `PRAGMA user_version`: version 1 is #6's schema exactly as merged (a file from #6 is at version 0 with it, and the step is a no-op there), version 2 is this issue's `ALTER TABLE session ADD COLUMN last_seq` and the two new tables. A version-0 file that already has `last_seq` or the outbox tables, which only a build of this branch from before the steps could make, fails step 2 and is not supported.
  On open, every step after the file's version runs, and the version is set, in one transaction. A file at a version newer than the binary knows is refused, so an old binary never lowers it.
  A step is never edited once merged; a schema change is a new step. No framework.
  whatsmeow keeps its own version in `whatsmeow_version` and never reads `user_version` [observed: go.mau.fi/whatsmeow store/sqlstore/container.go:85; no `user_version` in sqlstore or go.mau.fi/util dbutil]. Setting `user_version` inside the transaction is rolled back with it [observed: a throwaway probe on modernc v1.61.1 read 0 after a rollback that had set 7].
- **Seq in the transaction.** SQLite assigns the seq inside the one short write transaction; with one writer at a time, a live reader never skips a seq (`TestConcurrentRecordsNeverLetAReaderSkipASeq`, which killed an in-memory counter in 10 of 10 runs).
- **`busy_timeout(30000)`.** With every inbound message now a write, the integration suite on Windows CI failed writes with `SQLITE_BUSY` after the 5 s timeout: whatsmeow's device save in `LinkDevice`, and the outbox stress test's writers [observed: CI run 41344613539, win-x64; linux-x64 and osx-arm64 passed].
  A throwaway probe measured the cause on the runners (CI runs 41347105030 at 5 s and 41348002616 at 30 s; one writer alone, then 8 writers × 100 outbox transactions with 30 whatsmeow device saves between them) [observed]:
  - A commit alone under `synchronous(FULL)`: Windows p50 31-36 ms, p99 76-190 ms, max 99-700 ms; Linux p50 2.7 ms; macOS p50 1.1-1.3 ms.
  - No long holder: under the 8 writers a write transaction held the lock p50 5-6 ms, p99 21-100 ms, max 43-330 ms on Windows.
  - Waits for the lock on Windows: p50 0, p99 2 ms to 1.2 s, max 4.8-5.1 s. At 5 s, 1-2 of 800 transactions and 1 of 30 device saves failed with `SQLITE_BUSY`, each after waiting the full 5 s; at 30 s, none failed. Linux and macOS waited at most 1.7 s.
  - No deferred upgrade: every `BeginTx` of ours and of whatsmeow's dbutil is `BEGIN IMMEDIATE` through `_txlock=immediate`, no code issues a plain `BEGIN` (go.mau.fi/util dbutil and whatsmeow's sqlstore have none), whatsmeow's device save is one autocommit statement, and each failure above waited the full timeout instead of failing at once.
  So the cause is the busy handler's unfairness over Windows' slow commits, not a holder: a writer can lose its turn to a stream of short transactions for over 5 s. 30 s is six times the worst wait measured and still far below the node queue's 5-minute cutoff. A single write connection (mautrix-go's dbutil offers a write pool plus a read-only pool, database.go:293-320) would make waiting fair; it waits until a measurement asks for it, because `session.load` reads devices while it iterates its own rows.
  This supersedes ADR 0003's `busy_timeout(5000)`; ARCHITECTURE §5 has the new DSN.
- **Natural keys.** A message is keyed by kind, chat, sender and id, so whatsmeow's redispatch keeps its seq; a ConnectionStateEvent has no key. A repeat after every consumer acked its row and the row was deleted is recorded again with a new seq; the window is the milliseconds between our commit and whatsmeow's buffer clear, and `MessageId` plus `SessionId` dedupes it (events.proto says so). Key tombstones were rejected as a second, time-based retention for that window.
- **A sender-key-only part is not recorded.** A group message whose sender key is new is one stanza with a pkmsg or msg part that holds only the sender key and an skmsg part with the content (how whatsmeow itself sends one, send.go:795-831). whatsmeow dispatches a Message for each decrypted part with the same info (message.go:355-497, handleDecryptedMessage 1172-1178; processProtocolParts 938-961 filters nothing) [observed]. Recorded under one natural key, the sender-key part would take the key and the content would be dropped as a repeat while its receipt went out. A Message that is empty once its sender key and its context info are cleared is not recorded; whatsmeow stored the sender key itself. A repeat whose content differs from the recorded row never overwrites it: it is recorded beside it, under the key plus a SHA-256 of its payload marshalled deterministically, and logged as a warning. A duplicate is better than a loss, so a sender-key part with more than the key (an unknown field, say) still lets the content through; a true redispatch is byte for byte the same and keeps its seq, also under the derived key.
- **The handler.** Maps the event, records it, wakes the streams without blocking, and returns true only after the commit; false on a write error or a panic, with its own `recover`; never false because no consumer is connected. It is attached to every client by `cmd/whatsmeow-net`'s client factory, so the session slice does not know the Events slice.
- **`transition()`** records the stop state and the ConnectionStateEvent in one transaction. A restart that moves a paired session (to `Disconnected`, or to `LoggedOut{0}` when its device is gone) is a transition too, recorded at load.
- **Dispatcher bounds.** Events that finished behind an unfinished one keep only their seq. Nothing else bounds the order queue: other chats keep flowing past a stuck one, up to `MaxPending` events in flight at once, and a watermark that has not moved for a minute while events wait is logged once per stall.
- **Retention.** An event is deleted only once every consumer of its session acked it; a session with no consumer keeps everything. An abandoned consumer pins its session's rows, a known cost; a TTL waits until it is measured to matter.
- **A stuck send.** A stream whose client stopped reading blocks in `Send` on flow control, which only the stream's own end wakes, not a context derived from it (grpc-go http2_server.go:624, flowcontrol.go:54-66) [observed]. Each send runs on its own goroutine, and the stream returns on its context's end, so a replaced or stopped stream ends; grpc-go then finishes the stream, which ends the send.
- **Replacement.** A newer `StreamEvents` of the same session and consumer cancels the open one, which ends with `CONSUMER_REPLACED`; the cleanup of a replaced stream removes only its own registration (`TestTheReplacedStreamsCleanupLeavesTheNewOneRegistered`).
- **`DeleteSession`** deletes the session's outbox rows and cursors by `ON DELETE CASCADE` (#9's send records join with the same foreign key) and ends its streams with `SESSION_NOT_FOUND`.
- **The .NET side.** One fixed consumer, `client`: embedded mode has one client process per sidecar; External mode (#49) can make it an option.
  A session's events start flowing on its first successful `ConnectAsync` in the process, so handlers are registered first.
  The reader writes to a bounded channel; the dispatcher keeps at most 64 events received and unfinished, runs one lane per chat (and one for the session's state) in seq order, at most 16 lanes at once, and acks the watermark every second and at stop.
  At stop the handlers' token is cancelled; a handler that ends while it is cancelled, by returning or by throwing, has not handled its event, which comes again.
  A handler may delete its own session or dispose the sidecar (an application does it on `LoggedOut`): the stop does not wait for the lane while that lane still runs the event of the handler it is called from; the marker is the event, not the lane, so work a handler started that stops the dispatcher after the handler returned waits for the lane like any other caller. Lanes run on the thread pool, so a handler that blocks its thread does not stop the other chats.
  An event is mapped field by field: a time out of `DateTimeOffset`'s range is clamped, and a malformed alt JID is unknown, so the content still arrives. Only an event without a usable id, chat or sender is skipped and acked, like a payload case the client does not know, and logged; it never ends the stream. A failed ack, whatever it throws, is logged and tried again on the next tick and at the stop.
  A deleted session's client, or one of a disposed sidecar, throws `ObjectDisposedException` from `On`, `WaitForAsync`, `OnHandlerError` and `ConnectAsync`, and a pending `WaitForAsync` ends with it. The events end for good, logged as an error, on `SESSION_NOT_FOUND`, `CONSUMER_REPLACED` and `INVALID_ARGUMENT`.
  The limits are internal constants; options come with hosting (#39) if a user needs them.
- **Public API.** `IWhatsAppClient.On<TEvent>`, `WaitForAsync<TEvent>` (a handler in the same dispatcher), `OnHandlerError`; records `MessageReceived`, `UndecryptableMessageReceived`, `ConnectionStateChanged` with the fields events.proto has; `TextContent` and `UnknownContent`; `Jid` and `MessageId` at the root. Receipts come with #9, and the `[Experimental]` `Raw` property later.
- **Invariant 2** says "answered" instead of "acked", and names the answer: a delivery receipt for a message, an ack for a receipt or notification. Its meaning is unchanged: nothing of a gated kind is answered before it is durable.
- **The phone's copy is not gated.** An undecryptable message's content is recovered as a gated message only when the sender resends it; the phone's copy is best effort. This supersedes ADR 0003's line that the recovered message is gated; ARCHITECTURE §1 says it now. Reporting it upstream is left to the owner.

## Consequences

- A session's seqs have gaps, also from repeats SQLite spent a seq on; only their order is promised.
- An application that registers a handler after `ConnectAsync` does not get the events dispatched before it; the docs on `On<TEvent>` say so.
- A handler that ignores its token delays the disposal of the sidecar until it returns.
- A call can end with a `TaskCanceledException` from `MoveNext` instead of an `RpcException`, as one to a sidecar that is gone does [observed: `WatchDownTests`, and a logged-out session's reader when its sidecar was killed]. The reader and `WatchStateAsync` open the call again, after a 1 s pause unless the sidecar was launched again since the call opened; they never wait for a launch on it, since the same sidecar may still be up.
- Tests: a fresh file ends at the latest version, a version 1 file with a session upgrades and keeps it, reopening changes nothing, a newer file is refused (`internal/store/migrate_test.go`).
- Kill-either-process tests: `EventCrashTests` (the sidecar, on the shared fixture), `EventProcessTests` (the .NET side, through `SidecarHost events`, and a graceful stop on a clock that never moves).
- The fake WhatsApp does not persist its state across a sidecar kill; the kill tests kill only after an event is durable, and the window before the commit rests on the handler's false (Go tests) and on WhatsApp's redelivery (live, #10).
